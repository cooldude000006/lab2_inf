1. Задача: поиск и индекс

1.1. Что такое поиск

Поиск — нахождение в коллекции записей, у которых значение некоторого поля (ключа) удовлетворяет условию: равно заданному или лежит в диапазоне.

ПонятиеЧто это в нашей работе
Записьчеловек: номер, ФИО, год рождения
Коллекциямассив людей; порядок фиксирован
Атрибутполе или вычисляемое свойство: фамилия, возраст на 2019 год…
Ключзначение атрибута (или набора атрибутов) у записи
Позицияномер записи в коллекции

1.2. Зачем нужен индекс

Без вспомогательных структур найти запись можно только перебором — O(n) на каждый запрос. Отсортировать саму коллекцию по ключу нельзя: по условию задания порядок фиксирован, и к тому же сортировка годится лишь для одного ключа, а искать нужно по разным.

Определение

Индекс — отдельная структура «ключ → позиции записей с этим ключом», построенная над коллекцией по одному атрибуту. Коллекция не меняется; индексов по разным атрибутам может быть сколько угодно.

Именно так устроены индексы в базах данных: таблица хранится как есть, а для часто используемых полей заводятся индексы (обычно B+-деревья), в том числе составные и с поиском по диапазону (WHERE year BETWEEN 1990 AND 2000).

1.3. Виды запросов

  • По ключу (точное совпадение): все Ивановы.
  • По диапазону [low, high]: все, кто родился с 1990 по 2000.
  • По составному ключу: (фамилия, имя, год) = (Иванов, Пётр, 1995).

1.4. Почему «ключ → позиции», а не «ключ → позиция»

Ключ может повторяться: Ивановых много. Поэтому значение в словаре — список позиций, а сами ключи в словаре уникальны. Так оба наших словаря соответствуют интерфейсу IDictionary (уникальные ключи), а запрос по ключу сразу возвращает всех подходящих людей.

1.5. Почему позиции, а не указатели

Коллекция — динамический массив. При росте он выделяет новую память и переезжает, и все указатели на его элементы становятся висячими. Позиция же (номер в массиве) не меняется. Это вариант «1c» из пояснений к заданию: дерево хранит пары (значение, индекс в последовательности).

2. Порядок и сравнение ключей

2.1. Строгий слабый порядок

Бинарный поиск и деревья поиска опираются на одну операцию — «меньше» (a < b). Чтобы алгоритмы работали, она должна задавать строгий слабый порядок:

  1. Иррефлексивность: a < a — ложь.
  2. Транзитивность: a < b и b < c ⇒ a < c.
  3. Транзитивность несравнимости: если a ~ b и b ~ c, то a ~ c.
Равенство через «меньше»

Элементы эквивалентны (a ~ b), если ни один не меньше другого:

!(a < b) && !(b < a)

Так работают и наши структуры, и std::map: им не нужен operator==.

Пример нарушения

Вещественное NaN: NaN < x и x < NaN — оба ложь, то есть NaN «равен» всем числам, а числа между собой — нет. Транзитивность несравнимости нарушена, дерево поиска сломается.

2.2. Правило сравнения как параметр

Наши шаблоны принимают правило сравнения параметром: SortedSequence<T, Compare>, AvlTree<T, Compare>. Это функциональный объект (функтор) — класс с operator():

template <class K, class V>
class PairKeyLess
{
public:
    bool operator()(const Pair<K,V>& a,
                    const Pair<K,V>& b) const;
};   // сравнивает только a.key < b.key

Зачем: пары «ключ, значение» в дереве упорядочены по ключу, а == у самой пары сравнивает и ключ, и значение. Если бы мы переопределили < у пары «только по ключу», == и < противоречили бы друг другу — это «сюрприз» (Голуб, правило 145).

2.3. Лексикографический порядок

Так сравниваются слова в словаре и наши составные ключи:

  1. сравнить первые элементы; если различаются — ответ готов;
  2. иначе сравнить вторые, и так далее;
  3. если один ключ — начало другого, короткий меньше.
(Иванов, 2000) < (Петров, 1900)  // по фамилии
(Иванов, 1990) < (Иванов, 2000)  // по году
"Я" < "Яковлев"                  // префикс
Ловушка с диапазоном

Диапазон фамилий «А»–«Я» не включает «Яковлева»: «Я» — его начало, а начало меньше строки. Чтобы захватить все фамилии, верхняя граница — «я» (строчная): в UTF-8 строчные буквы идут после заглавных.

2.4. Строки в UTF-8

  • Русская буква занимает 2 байта. std::string сравнивает строки побайтно; для А–Я и а–я это совпадает с алфавитом.
  • Исключение: Ё (U+0401) стоит перед А (U+0410), ё — после я.
  • std::setw и length() считают байты, а не буквы: для ровных столбцов мы считаем символы сами (байты вида 10xxxxxx — продолжение символа).

3. Асимптотика

3.1. О-нотация

Определение

f(n) = O(g(n)), если f(n) ≤ c·g(n) для некоторой константы c и всех достаточно больших n. Говорит о росте времени с ростом n, а не об абсолютном времени.

  • O — оценка сверху, Ω — снизу, Θ — точная (и сверху, и снизу).
  • Константы и младшие слагаемые отбрасываются: 3n² + 5n = O(n²).
  • Основание логарифма не важно: log₂ n и log₁₀ n отличаются в константу раз.

3.2. Насколько это разные величины

Функцияn = 10³n = 10⁶
log₂ n1020
n10³10⁶
n log₂ n10⁴2·10⁷
n²10⁶10¹²

10¹² простых операций — это десятки минут; поэтому в эксперименте построение за O(n²) при n = 10⁶ пропущено.

3.3. Амортизированная сложность

Добавление в конец динамического массива иногда дорогое: когда массив полон, выделяется новый вдвое больше и все элементы копируются. Но в среднем по серии операций это O(1).

Доказательство

При n добавлениях с удвоением ёмкости копирования происходят на размерах 1, 2, 4, …, ≤ n. Всего копий:

1 + 2 + 4 + … + n < 2n

Значит, n добавлений стоят O(n), одно — O(1) в среднем. При увеличении ёмкости на константу (+10) копий было бы ≈ n²/20 — уже O(n) на добавление.

3.4. Как оценивать по графику

На графике с логарифмическими осями функция nk — прямая с наклоном k. Рост времени в 10 раз при росте n в 10 раз — линейный, в 100 раз — квадратичный. Для n log n — чуть больше 10 (у нас 12–19 раз).

Перебрать все записи и сравнить ключ каждой с запросом.

for i in 0 .. n-1:

Когда он лучше индекса

Когда запросов мало. Построение индекса стоит дороже одного перебора: у нас при 10⁶ записей АВЛ строится 1–4 с, а перебор — 0,1 с. Индекс окупается после примерно 10–40 запросов.

Роль в работе

Линейный поиск — эталон: он заведомо правилен, поэтому тесты и программа сверяют с ним результаты бинарного поиска и дерева.

5. Бинарный поиск

5.1. Условия применимости

  • Данные отсортированы по ключу.
  • Есть доступ по индексу за O(1) (массив). По связному списку бинарный поиск бессмыслен: дойти до середины — O(n).

5.2. Идея

Сравнить искомое со средним элементом и отбросить ту половину, где его быть не может. Каждый шаг уменьшает отрезок вдвое, поэтому шагов не больше ⌈log₂(n + 1)⌉: для миллиона — 20.

5.3. Две границы вместо «найти элемент»

Определения
  • LowerBound(x) — первая позиция, где элемент не меньше x.
  • UpperBound(x) — первая позиция, где элемент больше x.

Все элементы, равные x, занимают позиции [LowerBound, UpperBound).

Через две границы выражается всё:

  • есть ли x: i = LowerBound(x); i < n и a[i] ~ x;
  • сколько равных x: UpperBound − LowerBound;
  • диапазон [lo, hi]: от LowerBound(lo) до UpperBound(hi);
  • куда вставить: UpperBound(x) — после равных.

5.4. Код и инвариант

size_t LowerBound(const T& x) const
{
    size_t left = 0;
    size_t right = length;
    while (left < right)
    {
        size_t mid = left + (right - left) / 2;
        if (less(a[mid], x))
            left = mid + 1;
        else
            right = mid;
    }
    return left;
}
Инвариант цикла

Все элементы левее left меньше x; все элементы начиная с right не меньше x. В начале обе части пусты — верно. Цикл сохраняет инвариант и сужает [left, right); когда left = right, это и есть ответ.

UpperBound отличается одной строкой: условие less(x, a[mid]) → right = mid, иначе left = mid + 1.

5.5. Пример: LowerBound(7)

Массив: [1, 3, 5, 7, 7, 9, 11], n = 7.

Шаг[left, right)mid, a[mid]
1[0, 7)3 → 7: не меньше → right = 3
2[0, 3)1 → 3: меньше → left = 2
3[2, 3)2 → 5: меньше → left = 3
—[3, 3)ответ 3

UpperBound(7) = 5, значит семёрок 5 − 3 = 2.

5.6. Типичные ошибки

  • Переполнение: (left + right) / 2 переполняется на больших индексах; правильно left + (right − left) / 2.
  • Зацикливание: left = mid вместо mid + 1 при right = left + 1 оставляет отрезок прежним.
  • Смешение полуинтервалов: если right — «за концом», условие цикла left < right, а не ≤.
  • Беззнаковый тип: right = mid − 1 при mid = 0 даёт огромное число; полуинтервал [left, right) этого избегает.

5.7. Варианты деления (для общего развития)

  • Золотое сечение / Фибоначчи (модификации М-2.1, М-2.2): отрезок делится не пополам, а в пропорции ≈ 0,618. Число шагов чуть больше (≈ 1,44·log₂ n), но не нужно деление — исторически важно, когда деление дорого.
  • Интерполяционный поиск: точку деления угадывают по значениям (как в телефонной книге). На равномерных числах — O(log log n), в худшем — O(n).
  • Экспоненциальный поиск: сначала границу 1, 2, 4, 8… — для неограниченных или очень длинных массивов.

6. Отсортированная последовательность

6.1. Устройство

Массив, элементы которого всегда упорядочены. Вместо Append/Prepend/InsertAt один метод Add: место находится бинарным поиском (UpperBound), хвост сдвигается на одну позицию вправо.

Add(6) в [1, 3, 5, 7, 9]:
  UpperBound(6) = 3
  сдвиг 7, 9 вправо  →  [1, 3, 5, _, 7, 9]
  запись              →  [1, 3, 5, 6, 7, 9]

Поиск места — O(log n), но сдвиг — O(n). Именно сдвиг определяет время построения.

6.2. Стоимость построения из n элементов

Порядок данныхСдвигов всегоИтог
по возрастанию0 (всегда в конец)O(n log n)
по убыванию0+1+…+(n−1) = n(n−1)/2O(n²)
случайный≈ n²/4 (в среднем половина)O(n²)
Почему случайный ≈ вдвое быстрее убывающего

При вставке i-го элемента в случайном порядке его место равновероятно среди i + 1 позиций, и в среднем сдвигается i/2 элементов. Сумма i/2 по i = n²/4 — ровно половина от n²/2 для убывающих данных. Замеры это подтверждают: 10 с против 29 с при 10⁵.

O(n log n) на возрастающих данных — за счёт бинарного поиска места: сам сдвиг нулевой.

6.3. Почему «после равных» (UpperBound)

  • Порядок добавления равных элементов сохраняется (вставка устойчива).
  • На возрастающих данных, где ключи повторяются, вставка всё равно идёт в конец без сдвигов.

6.4. Словарь на двух массивах

Наш SortedSequenceDictionary хранит ключи в SortedSequence<K>, а значения — в параллельном ArraySequence<V> на тех же позициях.

  • Insert возвращает позицию ключа → значение вставляется туда же.
  • Значение (список позиций людей) можно менять на месте, а ключ снаружи — нельзя, порядок не нарушится.

7. Бинарное дерево поиска

7.1. Определение

Определение

Бинарное дерево поиска — дерево, где у каждого узла не больше двух детей и для любого узла все ключи левого поддерева меньше ключа узла, а все ключи правого — больше.

  • Высота — число узлов на самом длинном пути от корня до листа.
  • Симметричный обход (левое, узел, правое) выдаёт ключи по возрастанию.

7.2. Операции

Поиск: от корня: меньше — влево, больше — вправо, равно — нашли. Время O(h).

Вставка: спуститься, как при поиске, до пустого места и повесить новый лист. O(h).

Удаление — три случая:

  1. лист — просто удалить;
  2. один ребёнок — поставить ребёнка на место узла;
  3. два ребёнка — заменить значение узла минимумом правого поддерева (самый левый узел справа) и удалить этот минимум (у него нет левого ребёнка — случай 1 или 2).

Почему минимум правого: он больше всего левого поддерева и меньше всего остального правого — порядок сохраняется. Можно и максимум левого.

7.3. Беда: вырождение

Время всех операций — O(h), а высота зависит от порядка вставки: от ≈ log₂ n до n.

Упорядоченные вставки превращают обычное дерево в цепочку

На отсортированных данных обычное дерево становится списком: поиск O(n), построение 1 + 2 + … + n = O(n²). Решение — балансировка.

8. АВЛ-дерево

Адельсон-Вельский и Ландис, 1962 — первое самобалансирующееся дерево поиска.

8.1. Определение

Определение

АВЛ-дерево — дерево поиска, в котором у каждого узла высоты левого и правого поддеревьев различаются не больше чем на 1.

баланс(v) = h(левое) − h(правое) ∈ {−1, 0, +1}

Каждый узел хранит свою высоту — так баланс считается за O(1). Высота пустого поддерева 0, листа 1, узла: 1 + max(h(L), h(R)).

8.2. Теорема о высоте

Теорема

Высота АВЛ-дерева из n узлов: h < 1,44·log₂(n + 2), то есть O(log n).

Доказательство. Пусть N(h) — наименьшее число узлов в АВЛ-дереве высоты h. В таком «самом худом» дереве у корня одно поддерево высоты h − 1, другое — h − 2 (меньше нельзя по балансу), и оба тоже наименьшие:

N(h) = N(h−1) + N(h−2) + 1,  N(0) = 0,  N(1) = 1

h1234567
N(h)1247122033

Это числа Фибоначчи без единицы: N(h) = F(h + 2) − 1, а F(k) растёт как φk/√5, где φ = (1 + √5)/2 ≈ 1,618. Значит n ≥ N(h) ≈ φh, откуда h ≤ logφ n = log₂ n / log₂ φ ≈ 1,44·log₂ n. ∎

Для миллиона узлов — не больше 28 уровней (идеальное дерево — 20).

8.3. Повороты

После вставки или удаления баланс узла может стать ±2. Его исправляют поворотом — перестановкой трёх указателей, которая сохраняет порядок ключей и меняет высоты.

Малый правый поворот вокруг y; малый левый — обратная операция
Node* RotateRight(Node* y)
{
    Node* x = y->left;
    y->left = x->right;   // B переходит к y
    x->right = y;
    UpdateHeight(y);      // сначала нижний
    UpdateHeight(x);
    return x;             // новый корень
}

+2левый < 0левый у ребёнка, затем правый (большой правый)

Большой правый поворот: вставки 3, 1, 2 («левый-правый» перекос)

Малого поворота в случае «левый-правый» мало: средний ключ (2) оказался бы не там. Поэтому сначала поворачиваем ребёнка, превращая перекос в «левый-левый».

8.5. Вставка

  1. Спуститься как в обычном дереве, повесить лист.
  2. На обратном пути (рекурсия возвращается к корню) пересчитать высоту каждого узла.
  3. Если баланс стал ±2 — повернуть по таблице.
Не больше одного поворота

После поворота высота поддерева становится такой же, как до вставки, поэтому выше по пути баланс уже не меняется. Пересчёт идёт до корня (O(log n)), а поворот — максимум один (малый или большой).

8.6. Удаление

Как в обычном дереве (три случая), затем балансировка на пути к корню. Здесь поворот может уменьшить высоту поддерева, и перекос «поднимается» выше, — поворотов может понадобиться до O(log n). Время всё равно O(log n).

8.7. Поиск по диапазону [a, b]

Симметричный обход с отсечением ветвей:

Collect(node):
  if node == null: return
  if a < node.key:  Collect(node.left)
  if a ≤ node.key ≤ b: result.add(node)
  if node.key < b:  Collect(node.right)

В левое поддерево заходим, только если там могут быть ключи ≥ a, в правое — если там могут быть ≤ b. Посещаются: k найденных узлов и два пути вдоль границ a и b длиной O(log n). Итого O(log n + k), результат сразу по возрастанию.

8.8. Сложность АВЛ

9. Другие структуры поиска

9.1. Красно-чёрное дерево

Основа std::map и std::set. Каждый узел красный или чёрный; у красного нет красных детей; на любом пути от корня к листу одинаково чёрных узлов.

  • Высота ≤ 2·log₂(n + 1) — хуже, чем у АВЛ (1,44·log₂ n).
  • Зато при вставке и удалении не больше 2–3 поворотов, у АВЛ при удалении — до O(log n).
Вывод

АВЛ чуть быстрее на поиске (ниже дерево), КЧ — на частых изменениях. Для индекса, который в основном читают, АВЛ — хороший выбор.

9.2. B-дерево и B+-дерево

  • В узле — много ключей (от t−1 до 2t−1), детей — на один больше. Высота O(logt n): при t = 100 миллиард ключей — 5 уровней.
  • Узел — блок диска или страница памяти: одно чтение даёт сотни ключей. Поэтому B+-деревья — стандарт индексов СУБД (PostgreSQL, MySQL) и файловых систем.
  • B+-дерево: данные только в листьях, листья связаны в список → диапазон читается подряд.

9.3. Хеш-таблица

  • Хеш-функция превращает ключ в номер ячейки массива. Поиск, вставка, удаление — O(1) в среднем.
  • Коллизии (разные ключи в одну ячейку): списки в ячейках или открытая адресация (искать следующую свободную).
  • Коэффициент заполнения n/c; при переполнении таблица перестраивается (в задании — расширение в q раз при n = c и сжатие при n ≤ c/p).
  • Нет порядка ключей → нельзя искать по диапазону, нельзя выдать ключи по возрастанию. В худшем случае (все в одну ячейку) — O(n).

Зависимости — только сверху вниз: библиотека ничего не знает о людях, поэтому тестируется отдельно и работает с любыми типами.

10.2. Один интерфейс — два метода

Индекс хранит указатель на IOrderedDictionary<CompositeKey, ArraySequence<size_t>>. В конструкторе создаётся нужная реализация:

BinarySearch → SortedSequenceDictionary
Avl          → TreeDictionary
Linear       → nullptr (запросы идут
               в LinearFind)

Код запросов один: dictionary->Get(key), dictionary->GetRange(lo, hi). Это полиморфизм через виртуальные функции.

10.3. Построение индекса

for i in 0 .. n-1:
    key = attribute.MakeKey(people[i])
    if dict.ContainsKey(key):
        dict.Get(key).Append(i)
    else:
        dict.Add(key, {i})

Позиции добавляются по возрастанию → список каждого ключа уже упорядочен.

10.4. Результат — позиции по возрастанию

Диапазон даёт несколько ключей, у каждого — свой список позиций. Списки объединяются и сортируются слиянием: O(k log k). Зато результаты всех трёх методов одинаковы по форме и сравниваются простым ==, а пользователь видит людей в порядке коллекции.

10.5. Database: согласованность

  • Добавление человека: сначала проверить, что его ключ вычисляется для всех индексов, потом добавить в коллекцию и в индексы. Ошибка → ничего не меняется.
  • Замена коллекции: новые индексы строятся, пока старые целы; если что-то не построилось — откат к старым данным (строгая гарантия исключений).
  • Копирование запрещено: индексы хранят указатель на коллекцию базы.

10.6. Составной атрибут

CompositeKey — массив значений (число или строка) со сравнением лексикографически. Своя структура, а не std::tuple: набор атрибутов выбирает пользователь во время работы, а состав tuple фиксирован при компиляции.

11. Сортировка слиянием и перемешивание

11.1. Сортировка слиянием

  1. Разделить массив пополам.
  2. Рекурсивно отсортировать каждую половину.
  3. Слить две отсортированные половины: брать меньший из двух «голов».

T(n) = 2·T(n/2) + O(n) ⇒ O(n log n)

log₂ n уровней рекурсии, на каждом слияния в сумме обрабатывают n элементов. Время O(n log n) в любом случае, память O(n) на буфер.

Устойчивость

Сортировка устойчива, если равные элементы сохраняют взаимный порядок. Слияние устойчиво, если при равенстве брать элемент левой половины. Нужно генератору: записи с одинаковым годом остаются в порядке создания.

11.2. Тасование Фишера–Йетса

for i = n-1 downto 1:
    j = random(0 .. i)   // включительно
    swap(a[i], a[j])

Почему все перестановки равновероятны: на шаге с i выбор j из i + 1 вариантов. Всего исходов n·(n−1)·…·2 = n! — ровно столько, сколько перестановок, и каждая получается ровно одним способом.

Типичная ошибка

j = random(0 .. n−1) на каждом шаге даёт nⁿ исходов; nⁿ не делится на n!, значит какие-то перестановки вероятнее других.

В нашей работе замеры поймали ошибку: «случайный» порядок сначала совпадал с порядком создания, где номера и так возрастают. После перемешивания случайные данные стали строиться вдвое быстрее убывающих — как и предсказывает п. 6.2.

12. Как правильно мерить время

12.1. Правила

  • Только Release. В Debug нет оптимизаций, время в разы больше и искажено проверками.
  • Монотонные часы std::chrono::steady_clock: не прыгают при смене системного времени.
  • Повторы и медиана. Медиана устойчива к выбросам: одна задержка системы не исказит результат (среднее — исказит).
  • Одни и те же данные и запросы для всех методов — иначе сравнение нечестное.
  • Не дать компилятору выбросить код: результат поиска складывается в volatile-переменную, иначе «бесполезный» вызов могут удалить.
  • Разрушение старого индекса не входит в замер построения.

12.2. Кэш процессора

Память медленная: обращение в оперативную память — ~100 нс, в кэш L1 — ~1 нс. Процессор читает память блоками (строками кэша по 64 байта) и держит недавно использованное в кэше.

  • Массив лежит подряд → соседние элементы уже в кэше. Поэтому бинарный поиск и обход диапазона в массиве быстрые.
  • Дерево — узлы разбросаны по памяти; переход по указателю часто — промах кэша.

12.4. Два неочевидных эффекта

АВЛ: возрастающие вдвое медленнее убывающих

Спуск сначала проверяет ключ < узел, затем узел < ключ. Влево (убывающие данные) хватает первой проверки, вправо (возрастающие) нужны обе — сравнений на каждом уровне вдвое больше.

АВЛ: случайные медленнее упорядоченных

Асимптотика одна, но упорядоченные вставки ходят по одному краю дерева — эти узлы в кэше. Случайные вставки обращаются к узлам по всей памяти — промахи кэша (3,8 с против 0,9–1,7 с при 10⁶).

13. C++: сборка, шаблоны, классы

13.1. Как собирается программа

  1. Препроцессор заменяет #include содержимым файла, раскрывает макросы → единица трансляции.
  2. Компилятор превращает единицу трансляции в объектный файл (.o).
  3. Компоновщик (линкер) собирает объектные файлы и библиотеки в исполняемый файл, связывая вызовы с определениями.
ОшибкаПричина
redefinitionопределение попало в единицу трансляции дважды — нет защиты от повторного включения
multiple definitionфункция определена в .h и попала в несколько .o
undefined referenceобъявление есть, определения нет: .cpp не добавлен в сборку или шаблон не инстанцирован
  • #pragma once — защита от повторного включения заголовка (альтернатива — макрозащита #ifndef).
  • inline не обязывает подставлять тело, но разрешает одинаковое определение в нескольких единицах трансляции. Методы, определённые в теле класса, неявно inline.
  • using namespace в заголовке запрещён: он «заражает» все файлы, которые его включают.

13.2. Шаблоны

Шаблон — не код, а рецепт. Код появляется при инстанцировании — подстановке конкретных типов (AvlTree<int>). Компилятор должен видеть определение шаблона в месте использования.

Почему .h + .tpp

Если реализацию шаблона положить в .cpp, в других .cpp её не видно → «undefined reference». Поэтому объявление — в .h, реализация — в .tpp, который подключается в конце .h. Альтернатива — явное инстанцирование в .cpp (template class AvlTree<int>;), но тогда работают только перечисленные типы.

13.3. Интерфейсы и виртуальные функции

  • Чисто виртуальная функция (= 0) делает класс абстрактным — это интерфейс (IDictionary, ISortedSequence).
  • Вызов через указатель/ссылку на базовый класс идёт к реализации нужного наследника (через таблицу виртуальных функций).
  • Виртуальный деструктор обязателен у базового класса, если объект удаляют через указатель на базу: иначе вызовется только деструктор базы и будет утечка.
  • override — компилятор проверит, что метод действительно переопределяет виртуальный.

13.4. Правило пяти

Если класс владеет ресурсом (памятью) и ему нужен деструктор, нужны все пять:

  1. деструктор;
  2. конструктор копирования (глубокая копия);
  3. присваивание копированием;
  4. конструктор перемещения (забрать ресурс, источник — пустой);
  5. присваивание перемещением.

Без своего копирования оба объекта получат один указатель → двойное освобождение. У нас: ArraySequence, AvlTree. Index и Database копирование запрещают (= delete).

13.5. Копирование и обмен (copy-and-swap)

T& operator=(const T& other)
{
    T copy(other);  // может бросить
    Swap(copy);     // noexcept
    return *this;
}   // старые данные уходят с copy
  • Присваивание самому себе работает автоматически.
  • Если копирование бросит исключение (нет памяти), объект остаётся прежним — строгая гарантия.

Перемещение помечено noexcept: только тогда стандартная библиотека и наш код могут безопасно перемещать при переезде массива.

13.6. Исключения

  • Своя иерархия: Lab2Error → IndexOutOfRange, KeyNotFound, DuplicateKey, InvalidArgument, FileError, ParseError. Интерфейс ловит всё одним catch (const Lab2Error&).
  • Ловить по константной ссылке — без копирования и без «срезки» наследника.
  • Гарантии: базовая — нет утечек, объект корректен; строгая — при ошибке ничего не изменилось; noexcept — исключений нет.
  • Если конструктор бросил исключение, деструктор не вызывается — уже выделенное нужно освободить в самом конструкторе (так сделано в Index).

13.7. Мелочи, о которых спрашивают

  • explicit у конструктора с одним аргументом запрещает неявное преобразование (CompositeKey k = values; не скомпилируется случайно).
  • const-методы не меняют объект; константная пара Get возвращает const T&, неконстантная — T&.
  • Списки инициализации членов инициализируют поля до входа в тело конструктора.
  • size_t для индексов и размеров — беззнаковый и подходящей ширины.

15. Вопросы и ответы

1. Почему бинарный поиск — O(log n)?
Каждый шаг вдвое сокращает отрезок. После k шагов длина n/2k; отрезок исчезает при k ≈ log₂ n.
2. Можно ли бинарный поиск по связному списку?
Можно, но бессмысленно: дойти до середины — O(n), всего O(n). Нужен доступ по индексу за O(1).
3. Что вернёт LowerBound, если x больше всех?
n — позицию «за концом». Поэтому проверка «нашли» — i < n && a[i] ~ x.
4. Чем АВЛ лучше обычного дерева поиска?
Обычное на упорядоченных данных вырождается в список: поиск O(n), построение O(n²). АВЛ держит высоту ≤ 1,44·log₂ n всегда.
5. Докажите оценку высоты АВЛ.
N(h) = N(h−1) + N(h−2) + 1 — минимальное число узлов; это Фибоначчи, растёт как φh, значит h ≤ logφ n ≈ 1,44·log₂ n.
6. Сколько поворотов при вставке? При удалении?
Вставка — не больше одного (малого или большого): после него высота поддерева прежняя. Удаление — до O(log n): поворот может уменьшить высоту и перекос поднимется выше.
7. Когда нужен большой поворот?
Когда перекос «зигзагом»: узел тяжёл слева, а его левый ребёнок — справа (или зеркально). Малый поворот не исправит — сначала поворачиваем ребёнка.
8. Как удаляется узел с двумя детьми?
Его значение заменяется минимумом правого поддерева, а сам минимум удаляется (у него нет левого ребёнка).
9. Почему диапазон в дереве — O(log n + k)?
Обход с отсечением посещает k подходящих узлов и два пути вдоль границ длиной O(log n).
10. Почему отсортированная последовательность строится за O(n²) на убывающих данных?
Каждый элемент встаёт в начало и сдвигает все предыдущие: 0 + 1 + … + (n−1) = n(n−1)/2.
11. А на возрастающих — почему быстро?
Вставка всегда в конец (UpperBound = n), сдвигов нет; остаётся бинарный поиск места — O(n log n).
12. Чем отсортированный массив лучше дерева?
Меньше памяти (нет указателей), данные подряд — дружит с кэшем, быстрее обход диапазона. Хуже — вставка O(n).
13. Чем АВЛ отличается от красно-чёрного дерева?
АВЛ сбалансировано строже: высота 1,44·log n против 2·log n — поиск быстрее. КЧ делает меньше поворотов при изменениях.
14. Почему не хеш-таблица?
Она быстрее на точном совпадении (O(1)), но не хранит порядок ключей — нет поиска по диапазону, а он в задании (И-5.1).
15. Что такое индекс в СУБД и как он связан с работой?
Та же идея: таблица не переставляется, индекс хранит «ключ → адреса строк», есть составные индексы и BETWEEN. В СУБД обычно B+-дерево.
16. Почему индекс хранит позиции, а не указатели?
Массив людей при росте переезжает в памяти — указатели стали бы висячими. Позиции не меняются.
17. Как работает составной ключ?
Массив значений атрибутов; сравнение лексикографическое: по первому, при равенстве — по второму и т. д.
18. Почему диапазон «А»–«Я» не нашёл Яковлевых?
«Я» — начало строки «Яковлев», а начало меньше самой строки. Верхняя граница должна быть «я» (строчная).
19. Сортирует ли программа коллекцию?
Нет. Генератор раскладывает записи по ключу при создании — это подготовка данных для эксперимента. Созданная коллекция не переставляется.
20. Зачем линейный поиск в работе?
Эталон: заведомо верен, по нему проверяются оба индекса — в тестах и после каждого поиска в программе.
21. Когда индекс не окупается?
Когда запросов мало: при 10⁶ записей построение АВЛ 1–4 с, перебор 0,1 с — окупается после ~10–40 запросов.
22. Почему в замерах медиана?
Устойчива к выбросам: случайная задержка системы не исказит результат, в отличие от среднего.
23. Почему мерили в Release?
В Debug нет оптимизаций, время в разы больше и соотношения искажены.
24. Почему АВЛ на возрастающих данных медленнее, чем на убывающих?
Вправо — два сравнения на уровень, влево — одно.
25. Как проверялась корректность?
200 тестов: сверка с std::set, std::map, std::lower_bound и линейным поиском; инварианты АВЛ после каждой из 3000 случайных операций; граничные и некорректные значения.
26. Как проверялась память?
Санитайзеры ASan и UBSan, valgrind — на тестах и на сценарии работы программы: 0 ошибок, утечек нет.
27. Зачем шаблон в .h + .tpp?
Определение шаблона должно быть видно в месте инстанцирования, иначе «undefined reference».
28. Что такое правило пяти?
Класс, владеющий ресурсом, определяет деструктор, копирование (2) и перемещение (2). Иначе — двойное освобождение или утечка.
29. Зачем виртуальный деструктор у интерфейса?
При delete через указатель на базу вызовется деструктор наследника; без virtual — только базы, и ресурсы наследника утекут.
30. Почему TreeBuilder — отдельный класс?
Пояснение 3b задания: дерево не зависит от классов последовательностей, новые источники данных добавляются в построитель.
31. Как русские буквы работают в Windows?
Вывод — SetConsoleOutputCP(CP_UTF8); ввод из консоли — ReadConsoleW (UTF-16) с переводом в UTF-8; пути файлов — std::filesystem::u8path.
32. Почему результат поиска по возрастанию позиций?
Чтобы результаты трёх методов были одинаковы по форме и сравнивались простым ==. Цена — сортировка найденного, O(k log k).

Пять фраз, которые надо знать
  1. Индекс — «ключ → позиции», коллекция не меняется.
  2. LowerBound — первый не меньший, UpperBound — первый больший; равные между ними.
