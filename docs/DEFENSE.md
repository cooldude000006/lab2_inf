# ЛР-2. Шпаргалка к защите

## 1. Что сделано (одной фразой)

Над коллекцией людей, которую нельзя переставлять, строится **индекс** «ключ → позиции записей» по простому или составному атрибуту. Индекс устроен одним из двух способов — **отсортированная последовательность с бинарным поиском** или **АВЛ-дерево** — и сравнивается с **линейным поиском** по времени построения и поиска (по ключу и по диапазону).

**Рейтинг 59 при пороге 55:** И-5 (7) + И-5.1 диапазон (5) + И-5.2 составные атрибуты (7) + М-2 бинарный поиск (10) + ISortedSequence на Sequence (3) + М-3 бинарное дерево (15) + М-3.1 балансировка (7) + IDictionary на дереве (5).

5. «2 → 1», атрибут `7`, метод `2` (бинарный). «3 → 2 → 2» — диапазон 1990–1995.
6. «2 → 3» — содержимое индекса: ключ → позиции.

## 3. Алгоритмы

### Бинарный поиск (метод 1)
- **LowerBound(x)** — первая позиция, где элемент **не меньше** x; **UpperBound(x)** — первая, где **больше** x. Равные x элементы занимают `[LowerBound, UpperBound)`.
- **Инвариант цикла** (LowerBound): всё левее `left` меньше x, всё начиная с `right` — не меньше. Отрезок `[left, right)` каждый шаг вдвое короче → не больше ⌈log₂(n+1)⌉ шагов.
- `middle = left + (right − left) / 2` — без переполнения, в отличие от `(left + right) / 2`.
- Поиск ключа: `LowerBound` + проверка равенства. Диапазон `[a, b]`: от `LowerBound(a)` до `UpperBound(b)`.
- **Вставка**: место ищется бинарным поиском (O(log n)), но хвост массива сдвигается (O(n)). Отсюда O(n²) на построение по убывающим и случайным данным.
- Новый элемент встаёт **после равных** (`UpperBound`) — порядок равных сохраняется, а на возрастающих данных вставка всегда в конец, без сдвигов.

### АВЛ-дерево (метод 2)
- Дерево поиска, где у **каждого** узла высоты поддеревьев отличаются не больше чем на 1. Узел хранит свою высоту.
- **Почему высота O(log n):** минимальное число узлов в АВЛ-дереве высоты h: N(h) = N(h−1) + N(h−2) + 1 — как числа Фибоначчи, растёт как φʰ (φ ≈ 1,618). Значит h ≤ 1,44·log₂(n + 2).
- **Вставка**: спуск как в обычном дереве, затем на обратном пути пересчёт высот и поворот, если баланс стал ±2.
- **Четыре случая перекоса:**

  | Перекос | Как исправить |
  |---|---|
  | левый-левый (баланс +2, у левого ребёнка ≥ 0) | малый правый поворот |
  | левый-правый (+2, у левого ребёнка < 0) | левый поворот ребёнка, затем правый (большой правый) |
  | правый-правый (−2, у правого ≤ 0) | малый левый поворот |
  | правый-левый (−2, у правого > 0) | правый поворот ребёнка, затем левый (большой левый) |

- При вставке хватает одного (малого или большого) поворота; при удалении повороты могут понадобиться на нескольких уровнях вверх — O(log n) поворотов.
- **Удаление**: лист — просто удалить; один ребёнок — поставить его на место узла; два ребёнка — заменить значение минимумом правого поддерева и удалить этот минимум.
- **Диапазон [a, b]**: симметричный обход с отсечением — в левое поддерево заходим, только если значение узла > a, в правое — только если < b. O(log n + k).

### Индекс
- Словарь `IOrderedDictionary<CompositeKey, ArraySequence<size_t>>`: ключ → **позиции** записей (у многих людей одна фамилия).
- Код запросов один для обоих методов — работа через интерфейс; метод выбирается при построении.
- Результат — позиции по возрастанию у всех методов (для диапазона позиции упорядочиваются сортировкой слиянием, O(k log k)) → результаты разных методов сравниваются простым `==`.

### Составной ключ
- Набор значений (строка или число), сравнение **лексикографическое**: по первому значению, при равенстве — по второму…
- Начало ключа меньше самого ключа. Пример: диапазон фамилий «А»–«Я» **не включает** «Яковлев», потому что «Я» < «Яковлев». Чтобы включить, верхняя граница — «я» (строчная больше заглавных в UTF-8).

## 4. Сложность

| | Линейный | Бинарный поиск | АВЛ-дерево |
|---|---|---|---|
| Построение | 0 | O(n log n) по возрастанию; O(n²) по убыванию и случайно | O(n log n) всегда |
| Поиск по ключу | O(n) | O(log n) | O(log n) |
| Диапазон (k найдено) | O(n) | O(log n + k) + O(k log k) | O(log n + k) + O(k log k) |
| Вставка одной записи | O(1) | O(n) (сдвиг) | O(log n) |
| Память на индекс | 0 | 2 массива ключей и значений (подряд) | узел на ключ: значение + 2 указателя + высота |

## 5. Результаты эксперимента (n = 10⁶, Release)

- Поиск по ключу: **3–5 мкс** у индексов против **~96 000 мкс** у линейного — в 20–30 тысяч раз.
- Построение по номеру при 10⁵: бинарный поиск 95 мс по возрастанию, **29 с по убыванию**, 10 с случайно; АВЛ 75–204 мс при любом порядке.
- При 10⁶ бинарный поиск на убывающих и случайных данных пропущен: O(n²) заняло бы десятки минут.

**Два неочевидных эффекта** (подробнее в bench/README.md):
- АВЛ строится по возрастающим данным вдвое дольше, чем по убывающим: спуск вправо требует двух сравнений на уровне (`ключ < узел` — нет, `узел < ключ` — да), влево — одного.
- На случайных данных АВЛ медленнее, чем на упорядоченных, при той же асимптотике — промахи кэша: случайные вставки обращаются к узлам по всей памяти.

**Найденная замерами ошибка**: сначала «случайный» порядок генератора совпадал с порядком создания, где номера и так возрастают, — бинарный поиск на «случайных» данных строился быстро. Исправлено перемешиванием Фишера–Йетса, добавлен тест.

## 6. Сравнение с аналогами

| Аналог | Чем отличается |
|---|---|
| `std::lower_bound` по `std::vector` | то же, что наш метод 1; тесты сверяют наши границы с ним |
| `std::map` / `std::set` | **красно-чёрное** дерево: баланс слабее (высота до 2·log₂ n), зато меньше поворотов при вставке и удалении. Поиск у АВЛ чуть быстрее, изменения у КЧ-дерева чуть быстрее. Тесты сверяют наш словарь с `std::map` |
| Хеш-таблица (`std::unordered_map`) | поиск по ключу O(1) в среднем, но **нет поиска по диапазону** и порядка ключей |
| B / B+-дерево | много ключей в узле → мало уровней и обращений к диску; используется в индексах СУБД (PostgreSQL, MySQL). Листья B+-дерева связаны → диапазоны читаются подряд |
| Индекс в СУБД | наш индекс — та же идея: таблица не переставляется, индекс хранит «ключ → адреса строк», есть составные индексы и `BETWEEN` |

## 7. Решения, о которых спросят

- **Почему позиции, а не указатели на людей?** Коллекция — динамический массив; при росте он переезжает, и указатели станут висячими. Позиции не меняются. Это вариант 1c из пояснений (`Tree<Pair<T,int>>`).
- **Почему у сортированного словаря два параллельных массива?** Индексу надо дописывать позицию в список значения на месте. Ключи и значения отдельно → значение можно менять, а ключ снаружи — нет, порядок не нарушится.
- **Почему `PairKeyLess`, а не `operator<` у пары?** Правило сравнения — параметр шаблона. Пары в дереве упорядочены по ключу, а `==` у пары по-прежнему сравнивает и ключ, и значение — без сюрпризов (Голуб, правило 145).
- **Почему линейный поиск — тоже «индекс»?** Чтобы меню и замеры работали с тремя методами одинаково; у него просто нет словаря, и построение ничего не стоит.
- **Почему своя структура `CompositeKey`, а не `std::tuple`?** Состав ключа пользователь выбирает во время работы, а у `tuple` он фиксирован при компиляции.
- **Как построение отделено от дерева?** Класс `TreeBuilder` (пояснение 3b задания) — дерево не зависит от классов последовательностей.
- **Сортирует ли программа коллекцию?** Нет. Генератор раскладывает созданные записи по ключу для эксперимента — это подготовка исходных данных. Созданная коллекция не переставляется.
- **Где шаблоны и почему `.tpp`?** Определение шаблона должно быть видно в месте инстанцирования (методичка): иначе «undefined reference». Объявление в `.h`, реализация в `.tpp`, подключённом в конце `.h`.

## 8. Отступления от правил Голуба (и почему)

| Правило | Что сделано | Почему |
|---|---|---|
| 121 — результат через указатель, не ссылку | `Get()` возвращает `const T&` | идиома стандартной библиотеки; ссылка не бывает нулевой |
| 116 — избегать перегрузки | `operator<`, `==` у ключей; `Get` const и не-const | без сравнений шаблонные структуры не работают; пара const/не-const — стандарт C++ |
| 124 — `operator=` возвращает ссылку на константу | возвращает `T&` | как у всех типов стандартной библиотеки |
| 110.1 — без get/set | `GetLength`, `GetCount`, `GetFirstName`… | эти методы заданы спецификацией задания; сеттеров к полям нет |

Остальные правила соблюдаются; см. раздел «Правила оформления кода» в [PLAN.md](../PLAN.md).

## 9. Вероятные вопросы

1. **Почему бинарный поиск O(log n)?** Каждый шаг вдвое сокращает отрезок поиска; после k шагов длина n/2ᵏ, отрезок исчезает при k ≈ log₂ n.
2. **Можно ли бинарный поиск по связному списку?** Нет смысла: доступ к середине стоит O(n). Нужен доступ по индексу за O(1) — массив.
3. **Чем АВЛ лучше обычного дерева поиска?** На упорядоченных данных обычное вырождается в список: высота n, поиск O(n), построение O(n²). АВЛ держит высоту O(log n) всегда.
4. **Сколько поворотов при вставке в АВЛ?** Не больше одного (малого или большого): после него высота поддерева становится прежней, выше баланс не меняется.
5. **Что, если ключ повторяется?** Ключи в словаре уникальны; позиции всех записей с этим ключом собираются в список.
6. **Чем плох отсортированный массив, если он быстрее на возрастающих данных?** Вставка в середину — O(n); при постоянных добавлениях в случайном порядке дерево выигрывает.
7. **Когда линейный поиск лучше?** Когда запросов мало: построение индекса стоит больше, чем несколько переборов. На 10⁶ записей построение АВЛ ≈ 1–4 с, один перебор ≈ 0,1 с → индекс окупается после ~10–40 запросов.
8. **Почему время диапазона растёт с n?** В эксперименте ширина диапазона пропорциональна n (≈ n/1000 записей): растёт k, а время — O(log n + k log k).
9. **Как проверялась корректность?** 200 тестов: сверка с `std::set`, `std::map`, `std::lower_bound`, линейным поиском; проверка инвариантов АВЛ после каждой операции в 3000 случайных шагах; в программе — автоматическая проверка каждого поиска линейным.
10. **Как проверялась память?** ASan + UBSan и valgrind на тестах и на сценарии работы программы — 0 ошибок, утечек нет ([docs/memcheck](memcheck)).
11. **Почему медиана, а не среднее времени?** Медиана устойчива к выбросам: одна задержка системы не исказит результат.
12. **Что такое правило пяти?** Если классу нужен деструктор (он владеет памятью), нужны и конструктор копирования, присваивание копированием, конструктор перемещения, присваивание перемещением. У нас: `ArraySequence`, `AvlTree`. `Index` и `Database` копирование запрещают.
13. **Почему присваивание через «копирование и обмен»?** Присваивание самому себе работает автоматически, а при нехватке памяти объект остаётся прежним.
14. **Зачем `#pragma once`?** Защита от повторного включения заголовка в одну единицу трансляции — иначе «redefinition».
15. **Как русские буквы работают в Windows?** Вывод: `SetConsoleOutputCP(CP_UTF8)`. Ввод из консоли: `ReadConsoleW` (UTF-16) → UTF-8, потому что `std::cin` в консоли Windows не читает UTF-8. Пути файлов — через `std::filesystem::u8path`.
